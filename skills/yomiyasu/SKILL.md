# yomiyasu

「/yomiyasu」や「$yomiyasu」と名前のみで呼ばれ、推敲する文章を渡されなかったときは、直前の自分の返答に依頼を受けて書いた本文があればそれを推敲する（作業の報告や変更の説明は入らない）。そのような本文がなければ、作業フォルダの直下の `.md` と `.txt` のうち、`AGENTS.md` や `CLAUDE.md` のような指示のファイルを除いたファイルを推敲する。該当するファイルが2つ以上あればどれかを聞き、1つもなければ文章を貼るように頼む。

ファイルを選んで推敲したときは、最終稿を原文と同じフォルダにまだない名前で保存し、原文のファイルは書き換えない。「適用します」「有効にしました」と返すのみで終えない。

### 用途と表記の扱い
- 原文があれば推敲、資料（依頼文のみのときは依頼文）から書くなら新規作成とする。新規作成では依頼の読み手と目的に合わせ、資料にある事実で書く。原文と資料の両方があれば推敲として進める。
- 補助動詞と形式名詞の「事」「為」の漢字はひらがなにする（して下さい → してください、出来ます → できます、して頂く → していただく、して見る → してみる、する事 → すること、する為 → するため）。「事の経緯」のような中身のある名詞は残す。
- 他の表記の揺れ（外来語の長音、送り仮名、かなと漢字、全角と半角）は原文のままにする。

## 1. 基本原則

### 書き換えてよい範囲
この章の規則で書き直すときは、以下を変えてよい。
- 文と段落の順序（「構成と順序」）
- 段落の区切り
- 文の分け方と繋ぎ方
- 地の文と箇条書き・表の使い分け
- 言葉の選び方
- 同じ内容の繰り返しと、除いても読み手が何も失わない語句の削除（「冗長さの削減」）

原文の形から離れることは、書き換えを控える理由にしない。規則に当たらず自然に読める文は変えない。規則どうしで扱いが分かれるときは、読み手が前の文に戻らずに読めるほうにする。

### 意味の保持
書き換えても、以下は変えない。
- 主張: 何について何を述べるか。論点を別の概念にすり替えない。
- 否定と比重: 何を認め、何を否定するか。否定していたものを並列にしたり、順位を変えたりしない。
- 条件と範囲: 修飾・条件・限定・例外が掛かる範囲。
- 言い切りの強さ: 断定、推量、伝聞、許可（〜してよい）、能力（〜できる）、義務（〜しなければならない）、保証（必ず〜する）の強さ。伝聞や意見を断定に、依頼を説明に、仮定を予定に変えない。
- 誰が誰に: 動作をする人と受ける人。
- 数値・固有名詞・時期: 値、名前、日付、時制。完了したことを予定の「〜します」にしない。

これらを保てる言い方が見つからない所は、原文を残す。「冗長さの削減」で削る繰り返しと、原文が述べていない極端な主張を打ち消すのみの但し書きは、否定や条件を変えたことに入らない。

### 情報を追加しない
根拠にするのは、原文、依頼、資料、文脈（この会話の利用者の発言、開いたファイル、コマンドの出力）に書いてあることのみ。自分や他のAIの発言と一般の知識は使わない。原文から分からない動作主、原因、条件、数値、例、専門用語を推測で追加せず、ぼかした言葉をより狭い事実に置き換えない。要約の指定がなければ情報を省かない。同じ文書ですでに述べた内容の繰り返しと、原文が述べていない極端な主張（必ず、完全に、すべて）を打ち消すのみの但し書きは、ここで言う情報に入らない（「冗長さの削減」）。この規則は本文の後の欄にも適用する。

提供された定義、識別子、値と状態の対応は説明に活かす。出典のない「〜という声もあります」は本文に残し、出典が受け取り方を左右するときのみ尋ねる。

「昨日」のような相対の日付は、書いた日が確かに分かるときのみ括弧で日付を添える（昨日（3月4日））。essay と promo、すでに日付があるとき、他の日付と食い違うときは添えず、曜日は追加しない。添えたら「変えたところ」に何から数えたかを書く。

### 情報が足りない場合の暫定文
本文には、原文が読者に伝えている「未定」「調査中」も含め、主張・否定・条件・強さ・動作主をそのまま残す。読み取れないことの注記、質問、「要確認」のような編集表示は本文に入れず、理由は「変えたところ」、確認することは「書き手に確かめたい点」に置く。

意味を確定できなくても結びつく動作が分かる表現は、対象や仕組みを追加せずに本文に残す。質問は元から未定のことと読み取れないことを分けて尋ね、些細な不足を並べない。

### 文書の立場と文末
文末を選ぶ前に、誰が、誰に、何のために、いつのこととして書く文書かを確認し、主な用件と各段落で伝えることを決める。立場は以下の3つ。

| 立場 | 文書 |
|---|---|
| 勧め | 読み手に勧める・頼む文書（動くのは読み手） |
| 決まり | 運用ルール、手順書、お知らせ、仕様 |
| 説明 | 技術の説明、報告、体験 |

立場は掲載先と読み手、次に本文の手がかり（主語、宛名、署名、見出し）で決める。分野の名前（技術記事向け）のみでは決めず、決めきれなければ文末で決めない。

文末を修正するのは、動作主・時制・働きが意図とずれて読めるとき、文体を指定されたとき、掲載先と立場が合わないとき、「です・ます」と「だ・である」が意図なく混ざるとき。合わない文末を修正し、働きと強さ（勧めを義務にするなど）は変えない。

- 決まりの文書で規則そのものを書いた「〜しましょう」は「〜します」に揃え、理由の文と「〜してください」は残す。
- 語尾を散らすために働きを変えたり、文を繋いで「〜しましょう」を減らしたりしない。
- システムの動作（返します）、機能（できます）、依頼、予定、現在の方針（〜する方針です）は、それぞれの形を保つ。
- 変更の報告はどの指針・設定・実装をどう改めたかを述語まで書き、改定前が分からなければ比較を作らず、現在の動作や方針を今回変えたことにしない。
- 常体・敬体は指定がなければ原文のままにする。

立場を決めきれずに文末を変えたときは、もう一方の立場の文末を「書き手に確かめたい点」に1行で示す。

### 構成と順序
読み手が最初に知りたいこと（用件、結論、依頼、期限、読み手がすること）が段落や文書の後ろに埋もれていれば、前に出す。前置き、経緯、理由はその後に置く。
- メール、お知らせ、報告、PR の説明、障害報告の冒頭は、用件か結論から始める。
- 段落の中でも、言いたいことを述べる文を先に置き、理由や例を後に続ける。
- 1段落に話題が2つ以上あれば段落を分け、同じ話題が離れた段落に散っていれば1か所にまとめる。
- 3つ以上の並列の項目、手順、条件の組み合わせが地の文に詰まって読みにくければ、箇条書きか表にする。逆に、論理が繋がった説明を箇条書きで切っているときは地の文に戻す。

以下の順序は、それ自体が内容なので並べ替えない。
- 時系列（経過、議事の流れ、体験、物語）
- 手順の順序と番号
- 条文、台詞、スライドのページのように、番号や位置で参照される単位
- 前の文を受けて後の文が成り立つ推論の積み上げ

依頼で構成や見出しの形を指定されたときは、それに従う。順序や構成を変えたら「変えたところ」に1行で書く。

### 主語と目的語の明確化
「誰が、何を、どうした」は、原文・依頼・資料・文脈に書いてある言葉のみで補う。元にない担当者や動作主を作らず、システムの動作を人の行為に変えず、近くにある名詞という理由のみで対象を選ばない。指示語を名詞に戻すのは指す先が決まるときのみ。何の期限か、何を頼むかが抜けて読み違えるときは、同じ文書の前後の言葉で補い、2つ以上に読めれば尋ねる。

文の形ごとの扱いは以下のとおり。
- 目的語を書かない他動詞の前に句が挟まり、前の別の名詞が目的語に読める文は、書いてある対象を目的語に書くか、動作を名詞にして主語に立てる。
- 主題が部品の名前で後半に別の名前の動作が続き、その主題の話か決まらない文は、主体を追加せずに尋ねる。
- 動作主が切り替わる所は主体を書き、使役の述語は変えずに主語の側を「〜には」に修正する。
- 書き手の一人称（私は）を追加するのは、依頼で書き手を言われたときのみ。

主語と述語の間に別の主語のある節が挟まると、前の主語が節の動詞の主語に読める（部長が新人が会議で発言することをやめさせた）。読み手が前に戻らないと誰が何をするかが分からないときのみ、長い節を主語の前に出し、主語を述語のすぐ前に置く（新人が会議で発言することを部長がやめさせた）。前の文からその主語の話が続いていれば、主語を「は」にして文の初めに残してもかまわない。

語順を変えないのは以下のとき。
- 文が長い、または主語と述語が遠いという理由のみのとき
- 主題の「は」の後に「が」の節が続く文（このツールはファイルが更新されたことを知らせる）
- 主語を述語の前に寄せると、原文にない強調や対比が出るとき
- 文頭の「は」が後ろの文まで話題を決めているとき

語順を変えても、述語ごとの主語と相手、使役と受け身、否定や限定の語（だけ、のみ）の掛かる範囲は元のままにする。文頭の条件や時の句は文頭に残し、言葉は追加しない。節の動作を誰がするかが2通りに読めるなら、語順で一つに決めずに尋ねる。補う主語も述語のすぐ前に置き、別の主語のある節より前には置かない。語順を変えたら述語ごとの主語を原文と読み比べ、「変えたところ」に書く。

### 段落と文の論理構造（つながり）
接続語、主題の「も」、文頭の指示語は、何と何を繋ぐかを確認し、根拠が前後にあれば正しい言葉に修正し、なければ尋ねる。予告のみの文は予告の重みを述語に残して続く文と1文にする。「重要なポイントは3つです」のような数の予告は、数と項目が合うときのみまとめ、合わなければ数も項目も変えずに尋ねる。

文の組み立ては以下のように扱う。
- 主述のかみ合わせを修正し、動作を名詞にした主題に必要なことが続く文は「ログを一括で削除するには、」の形にする。
- 修飾・条件・否定・因果・時系列の掛かる範囲を保ち、見聞きした日時を出来事の日時にしない。
- 2通りに読める所は一つの読みに決めず尋ねる。
- 長くて掛かり方を追いにくい文は分ける。分けるときは、手段・理由・順序・対比の関係を後ろの文の接続語で残す。
- 原文の1文から「〜ためです。」の短い文を切り出さず、「〜ます。」の短い文を続けすぎず、同じ対象や場面は意味のまとまりで1文にする。
- 改行は話題や段階が変わり、分けると読みやすい所に入れる。

本文で言い終えたことを同じ強さで言い直すのみの締めの文や「まとめ」は削る。新しい情報や絞り込みがあるもの、長い文書の要約、依頼で指定されたまとめ、報告やお知らせの最後で次にすることや予定を述べる文は残す。削る前に、そこにしかない数値・条件・例外がないかを確認し、あれば残すか本文へ移す。

### 冗長さの削減
同じ文書で2回以上述べた内容と、除いても読み手が何も失わない文や語句は削る。削る前に、その箇所にしかない数値・条件・例外・理由がないかを確かめ、あれば残すか、残す側の文に移す。削るか迷うときは `references/redundancy.md` の例を読む。

| 型 | 手がかり | 直し方 |
|---|---|---|
| 内容の繰り返し | 冒頭の結論、本文、まとめ、箇条書きや表と直後の地の文、段落の最後の「つまり、〜」が同じことを述べる | 1か所に残す。結論は前に残し、本文の側は根拠と詳細を述べる文にする。 |
| 打ち消すのみの但し書き | 「〜わけではない」「〜とは限らない」「〜という意味ではない」が、本文の述べていない極端な主張（必ず、完全に、すべて）を打ち消す | 削る。同じ文に新しい事実があれば、その事実を肯定の文で残す。 |
| 言い直しの括弧 | 前に出た語の原語や略語をもう一度書いた括弧、読み方をカタカナで書いた括弧、直前の語を同じ意味で言い直した括弧 | 括弧を除く |
| 近い意味の語の並び | 「確認・検証」「把握・理解」「数学的・論理的に」のように、中黒や「や」で並べた語を後の文で区別しない | 述語に合う1語にする |
| 中身のない副詞 | 実際に、完全に、明示的に、しっかり、さまざまな | 除いても主張が変わらなければ除く |
| 案内のみの文と節 | 直後の見出しを並べ直した「本記事の構成」、「〜を整理すると以下のとおりです」 | 削るか、続く中身と1文にする（`references/slop-catalog.md` 6章） |
| 共通する条件の繰り返し | 一覧や表の全ての項目に、同じ条件や注意（「〜ときのみ」「分からなければ残す」）を項目ごとに書く | 一覧の前に1回書き、項目からは除く。 |
| 主題の繰り返し | 続く文の文頭に毎回同じ主題（「TCPは」）を書く | 2文目以降の主題を省くか、1文にまとめる |

以下は削らない。
- 本文のどこにもない条件・限界・数値を述べる但し書き（「上の数字は Node.js v24 で測った値です」）。本文の主張に掛かる条件なら、その文の中に条件として入れてもよい。
- 読み手が知らないかもしれない語の、初めて出た所の原語と説明（`references/audience.md`）。
- 並べた語がそれぞれ別の物や作業を指し、本文がその全てを扱うときの並び。
- 「必ず」「確実に」のように保証を表す副詞（「意味の保持」の言い切りの強さ）。
- 長い文書の冒頭の要約と、依頼で指定された要約とまとめ。
- formal の定義と条件の繰り返し、manual の手順ごとの前提と警告、essay・promo・script で書き手が意図した反復、incident の経過と影響の節に同じ事実がある所。

削った所は「変えたところ」にまとめて1行で書く。

### セルフラベリングと否定対比の整理
否定対比（AではなくB）は、Aを除いても主張が変わらないときのみ肯定文にする。誤解を正す否定（「原因はキャッシュではなくDNSの設定でした」）は残し、Aを並列や順位づけに変えない。「弱みではなく視点の違いでもある」は一つの文のまま残し、直前に挙げた二つをどちらも打ち消すのみの文は「どちらでもない。」と受けて構わない。

用語の説明が「〜ではありません」のみで薄いときは、原文や資料から何であるかを先に書き、否定は後に残す。「重要なのは」が評価を担っていれば述語に移して残し、理由・対比・結論を示す前置きは残す。

### 内容に合わない大げさな名詞の整理、専門用語と名称の扱い
規則を「契約」、原文を「正本」、確認を「ゲート」、一覧を「台帳」のように大げさに呼ぶ言葉は、実際の役割の言葉に修正し、元にない信頼性や唯一性を追加せず、元の強さも弱めない。正式な名称や専門用語としての用法（品質ゲート、行政の台帳）は残す。「分離」「保証」「管理」のような漢語の名詞や「〜を行う」のみで動作を済ませた文は、原文や資料に動作と条件があるときのみその文に書き直し、なければ残して尋ねる。

専門的な意味の言葉はその分野で定着した用語で書き、文字どおりの日常語は専門用語に変えず、識別子、画面の項目名、API の名称・型・値、引用した原文は変えない。意味の決まらない言葉を近い印象の言葉に置き換えない。

### 比喩動詞の具体化と擬人化の解消
「倒す」「効く」「溶かす」「潰す」のような比喩動詞は、何がどう変わったかを書くか、普段の表現にする。効き目のみをぼんやり言う形（「助けになっている」）にしない。「うっかり」「ようやく」「〜てしまった」「地味に」のような含みは別の言葉で残し、原文より強い確度の言葉（確実に、必ず）は追加しない。

データやシステムの「壊れる」は「おかしくなる」「使えなくなる」のように同じ広さの言葉にし、整合性の話だと分かるときのみ「整合性が失われる」にする。システムやデータの不具合や変化について、知らせが出ないことを「静かに」「黙って」とぼかしているとき（「静かに壊れる」「黙って失敗する」）は、「気づかないうちに」「知らないうちに」のように気づけないという幅のまま書く。それ以外の「静かに」（人や物の様子、「議事録が会議の迷いを静かに語っていた」のような擬人化）は、この言い換えに適用しない。比喩なら比喩と擬人化の規則のとおりに修正し、原文にない「気づかなかった」という含みを追加しない。

「骨が折れる」のような慣用句は残す。エッセイと小説では、何を何に例えたか読める比喩は残し（エッセイの比喩動詞は修正する）、主語と述語を取り出すと成り立たず連想もできない比喩（「午後が膝を抱える」）は修正し、後の文で例えた理由を述べた比喩は残す（`references/slop-catalog.md` 8章）。

道具や概念に感情や意志を持たせた擬人化（「コードが語る」）は修正し、以下は残す。
- 働きを客観的に述べる文（「このツールはログを集めます」）
- 働きが一読で分かる擬人化（「センサーが異常に気づく」）
- 開発者向けの文書で識別子が主語の文

人の判断を抽象名詞の作用のように書いた文（「見積もりの甘さが判断を遅らせた」）は、誰の行動か分かるときのみ書き直す。コードを人の知識や役目にたとえた表現（「呼び出し元の事情を知っている」）は、コードや資料に実際の動作が書いてあるときのみ、何を受け取り、何を返し、何を呼ぶかの文に修正し、分からなければ残して尋ねる。設計の用語（責務を持つ、依存する）と、原文や資料がその用語で書いたオブジェクト指向の「〜はデータを知っている」は残す。

次の修正は lint に出なくても適用する。

### 文長と読点の調整
短い主題（は、も、には、では）、短い主語の「が」、短い目的語の「を」のすぐ後で間を作るのみの読点は除き、新しく追加しない。

残す読点は以下のとおりで、他は何か所あっても除く。
- 誤読を防ぐ所（「店長は、慌てて逃げた客を追いかけた」）
- 主題の後に別の動作主が続く所（「会議では、担当者が説明しました」）
- 文頭の場面の枠の後で文が長く、除くと区切りが見えにくくなる所
- 長い主語や節の後、定義の「〜とは、」の後、挿入句の前、並べた語句の間
- 条件・逆接・理由の切れ目、文頭の接続語の後（まず、また）

区切りがどれも短い文では副詞（毎日）の後の読点も除く。「1つ目は、」のような項目の先頭の主題の後、「AではなくB」の「なく」の後、見出しの中の読点も除く（文書の題は変えない）。除くのは読点のみで、語順と述語は変えない。lint の pause_comma の候補は残す読点に当たらなければ除き、候補に出なかった同じ形の読点も同じ決まりで見る（lint は全てを拾わない）。小説や随筆で書き手が間として置いた読点は残してかまわない。

### 太字とラベル
箇条書きの先頭のラベルとコロン（`- **期限**: 11月末`。太字でなくても同じ）は、コロンの後が値か説明の文かで分ける。

| コロンの後 | 扱い |
|---|---|
| 日時・場所・担当・数値・状態のような値 | ラベルとコロンを残す |
| 物や方式、引数、設定項目、作業の名前に続く説明 | ラベルとコロンを残す |
| 値の項目が並ぶ中の1項目 | ラベルとコロンを残す |
| ラベルが説明の文をまとめたのみの言葉（「特徴」のような分類の言葉、出来事を名詞にした言葉、短い述語） | 太字とラベルとコロンを除き、ラベルの意味を説明の最初の文に入れて1文にする |

最後の行の例は `1. **応答速度の低下**：ピーク時に3秒を超えた。` → `1. 応答が遅くなり、ピーク時に3秒を超えた。`。勧める動作のラベル（`**手順書を読む**:`）は、「読むときは」のような条件にしない。ラベルの場面と説明の文の条件が別のもの（`**停電時の対応**:電源が使えない場合は`）なら、2つを1つの条件にまとめず、ラベルとコロンを残して太字のみを除く。

説明の文にないラベルの言葉は省かずに文へ入れ、1文にする（`- **鍵と名札の返却**：帰る前に受付に返却する。` → `- 帰る前に鍵と名札を受付に返却する。`）。入れた後で、条件や否定、「〜し、」で続けた節の掛かる範囲が変わったら、ラベルとコロンの形に戻す。

太字のラベルとコロンで始まる項目が2つ以上重なるときは、残すラベルの太字も多用として除く。議事録とスライドのラベルと値、紹介記事・宣伝文の見出しの太字の行はこの扱いの外とする。

### 2文の否定対比と「もちろん、」
否定と肯定を2文に分けた形（「必要だったのは新しい道具ではない。使い方をそろえることだった。」）は、否定を残して1文にまとめ、「なく」の後に読点を追加しない。エッセイでも同じ。小説の語りと会話、紹介記事・宣伝文で短い文を重ねた所、後ろの文が別の主張を追加しているときは除く。

文頭の「もちろん、」に数語のみが続く短い文（「もちろん、失敗もする。」）は随筆でも「もちろん、」を除き、別の言葉で補わない。会話や引用、答えの「もちろんです。」、後ろに具体的な内容が続く文は対象外とする。

### 案内用の見出し
見出しはその節で何を扱うかが分かる短い項目名（「保存期間」「材料を量る」）にし、語り出し、理由、警告・条件・結論を文のまま詰め込まない。形は以下のように扱う。
- 節を見分ける手がかりの言葉（「Issueに残す採用理由」）は残す。
- 見出しは「AではなくB」の形にせず、Bの側のみを書く。
- 後ろの括弧と結びの「〜について」は除き、管理番号、社内の呼び名、画面の項目名の括弧（「（REQ-118）」）は残す。
- 「jqとは：使い方」は「jqの使い方」にする。
- 本文に出てこない一語の比喩の見出しは、本文の言葉で項目名にする。

見出しから除いた警告・条件・結論、範囲・順序・手段、書き手の評価や態度は省かず、本文になければ本文へ移す。節の役割を示す言葉（「まとめ」「はじめに」）は、見出しを短くするときも除かない。

依頼で指定された見出しの形とまとめの節、文書の題、議事録の見出し、紹介記事・宣伝文のキャッチコピーは修正しない。

### 装飾記号の排除と太字の表示、コピー調の抑制
絵文字、文末の装飾のコロン、ダッシュ（em dash、「─」「──」）、情報の増えない言い換えの括弧は除く。ラベルと値のコロン（「日時：10時」）、URLやコード、罫線の区切り線、出典の記号は残す。ダッシュを除いて1文に繋ぐと前の理由や条件が後ろまで掛かるなら、2文にする。手順や先に済ませる作業を括弧に入れた文は、括弧から出して行う順番に並べる。原文の「■」「・」は Markdown に置き換えず、英数字の前後の空白は一律に追加したり削除したりしない。

「資料を、全員へ。」のように短い句で切るコピー調、「速い。軽い。安い。」のように評価の言葉のみを並べる型は、対象と動作が原文から決まるときのみ述語まで書く。評価の言葉を追加したり強めたりせず、対象が決まらなければ残す。「〜したのは、A、B、C。」は、前提が前の文や見出しにないときのみ「〜では、A、B、Cが変わった」にする。

promo では勢いを残し、根拠のない誇張は本文を変えずに尋ねる。

### 直訳語、漢語の詰まり、連用形名詞
直訳語（機械やシステムが人の動作をする言い方、実物の代わりの場所のたとえ、英語を一語ずつ写した句、英語の短い術語に当てた漢字1字の名詞、英語の術語に当てた2字以上の名詞）は、その分野の人が自分で書くときに使う呼び名か、英語に戻すと一語ずつ対応するか、の2つを問う。修正するときは、何が何をどうするかを前後の文から確認して文として書き直し、言葉を差し替えるだけで済ませない（術語を訳した名詞を定着した呼び名に置き換えるのは差し替えに入らない）。名前と動作が原文や資料になければ残して尋ねる（型と例は `references/calques.md`）。

助詞を省いて漢語を詰めた句（「書類不備発見時は」）は、言葉を残して助詞と動詞を補ってほどく。ほどくと「とき」が近くで続くなら、「時」「際」を残すか、ほどかない。定着した複合語（ログイン画面）と正式な言葉は詰まりとして扱わない。

漢語と和語の選び方は原文のままにする。その文書で普通に使う漢語（確認する、使用する、停止する、動作する、現在、現時点）は和語の表現に置き換えず、報告書の「発生」も残す。和語に置き換えてよいのは、中身のない硬い漢語（多角的、包括的、活用する。`references/slop-catalog.md` 7章）、決まり文句、比喩、名詞化の表現（〜を実施する、〜することが可能です）のように、他の規則で修正する所のみ。そこでも文書の硬さに合う言葉にし、和語の動詞に置き換えるのは目的語が文の中で追え、意味の幅が同じときのみにする（「確認する」は「見る」にしない）。

書き直した所に、原文にない漢語や名詞化の表現（担保、〜の実施）を追加しない。ペルソナで敬語を上げる言い換え（同じこと → 同様のこと）と、読み手を general に指定されたときの言い換え（`references/audience.md` 8章）は、この規則の外とする。新規作成でも、資料の漢語を和語の表現に置き換えない。

他動詞の連用形を1語のみ名詞にして「の」で受ける形（「結果の確かめ」）は、「結果を確かめる」か定着した漢語（結果の確認）にする。「資金集め」「見直し」のような定着した言葉は残し、漢語を和語にひらくときもこの形を作らない。

## 2. 実行手順

### Step 1: 種類と読み手
- 種類と読み手は、依頼と本文の手がかりのみで決める。種類は pr、article、incident（障害報告）、proposal、minutes、manual、slides、essay（エッセイ・小説）、formal（公用文、規程、契約書、仕様書）、promo（紹介記事・宣伝文）、mail（メール・チャット）、paper、script（台詞・脚本）の13種類で、当たらなければ決めない。種類を決めたら、書き直す前に必ず `references/doc-types/<種類>.md` を読み、そこで適用しないとした規則を適用しない（書き方に迷うときは `references/domains/` の該当するファイルを読む）。
- 読み手は expert、informed、general の3段階。指定に従い、分からなければ決めない。informed か general を指定されたら `references/audience.md` を読む。その読み手に説明の必要な用語で原文と資料に説明がなければ、言葉を残して「ここに説明が必要です: 言葉（場所）」と書く。
- 決め方で修正の仕方が変わり、問い返せるときのみ、書き直す前に1回のみ確認する。本文のみの指定、非対話の実行、他のスキルの途中、「質問しないで」のときは決めずに進む。
- 書き手の立場と読み手との関係（上司、取引先など）は、依頼で言われたときのみ使い、`references/persona.md` を読んでから修正する。上司と社外の読み手への依頼と読み手の行為は尊敬語に、社外に向かう書き手の行為は謙譲語に上げ、「お・ご」を付けるだけでなく、その関係で人が普通に書く表現にする。言われないときはペルソナを理由に敬語も書き手の主語も変えず、ペルソナや敬語について、変えなかったこととその理由を返答のどこにも書かない。
- 作業フォルダのある git リポジトリのルート（git の外では作業フォルダ）に `.yomiyasu-words/` があれば、`allow.txt`（修正しない言葉）、`flag.txt`（見直す言葉。直訳語と同じく文として書き直す）、`flag-patterns.txt`（見直す言葉の名前と正規表現。flag.txt と同じ扱い）を読む。

### Step 2: 読み手として読み、直す
1. 原文に lint をかける（`python3 ${CLAUDE_SKILL_DIR}/scripts/yomiyasu_lint.py 元の文.md`。コマンドは「実行するコマンド」の節のとおり。種類を決めたら `--doc-type 値`、読み手を決めたら `--reader 値` を追加する）。候補は手がかりの一部で、修正する合図ではない。候補が0件でも1章の型を探し、それのみを理由に原文のまま返さない。直訳語の指摘が出た文は「直訳語」の2つの問いで読み直す。指摘ごとの見方は `references/review-points.md`、ai_phrase の問いは `references/slop-catalog.md` 10章にある。
2. 型を探す前に、原文を上から1回、初めて読む読み手として読み、読み手が止まる所を書き出す。書き出すのは以下のような所。
   - 用件や結論が後ろにあり、最後まで読まないと何の文書か分からない所
   - 前に戻らないと誰が何をするか、何を指すかが分からない所
   - 動作をする人が文の中にあるのに受け身で書いた所（「担当者から案が示された」）
   - 助詞を省いて名詞を詰めた所
   - 掛かり方を読み違える所
   - 同じ言葉や表現が近くで続く所
   - 前に読んだことをもう一度読まされる所と、除いても何も失わない語句（1章「冗長さの削減」）

   書き出した所は1章の型に当たらなくても修正する。読み手にとって何が読みやすくなったかを言えない案は使わない（このメモは出力には出さない）。1章は本文の全ての文に適用するが、単調さを修正する目的のみで自然な文の語尾を変えない。
3. 構成と順序を先に決め（1章「構成と順序」）、その後で文を直す。順序を変えた段落も、文の規則は同じように適用する。
4. 本文は前後の文を読んで修正する。sed、perl、python などの置換で本文をまとめて修正しない（正規表現で同じ形の行をまとめて変える、置換の組を一度に流す、など）。太字のラベルや「〜は、」の読点のように同じ形の箇所が続くときも、1か所ずつ修正するかを決める。最終稿は修正した全文をファイルに書くか、1か所ずつ修正する。

### 実行するコマンド
lint は `python3`、`python`、`py -3` の順番に試して、command not found か「Python was not found」で終わったら同じ引数で次を試す。どれも動かなければ `references/review-points.md` 4章の観点で目視で点検し、確認の記録の「実行した検査」に「なし（Python がないため lint を実行しなかった。観点を目で点検した）」と書く。

`${CLAUDE_SKILL_DIR}` はこのスキルのフォルダで、置き換わらずに残っていれば SKILL.md のあるフォルダの絶対パスに書き換える。コマンドには `cd`、`&&`、出力のリダイレクト（`>`、`2>&1`）を付けない。ファイルに保存しないよう頼まれたときは、ファイル名の代わりに `-` を渡し、本文を標準入力から渡す。標準入力では以下のように渡す（`printf` や `echo` の出力をパイプで渡さない）。

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/yomiyasu_lint.py - <<'YOMIYASU_EOF'
（本文）
YOMIYASU_EOF
```

### Step 3: 最終稿を読み直す
- 最終稿を原文とは別のファイルに保存し、原文と同じ引数で lint をかける（「実行するコマンド」の節）。
- 最終稿を読み手として上から通読し、用件と誰が何をするかが最初の段落で伝わるか、前に戻らずに読めるかを確認する。止まる所があれば直す。
- lint に残った info の指摘は、その文を Step 2 の問いで読み直し、直すか、残す理由を「残したAI特有の表現」に書く（理由のみで済ませるのは、定着した表現と文字どおりの意味のときのみ）。
- 原文と最終稿で地の文の読点の数を比べ、増えた読点が「文長と読点の調整」の残す読点に当たらなければ除く。最終稿の lint に残った pause_comma の読点と、候補に出なかった文頭の「〜は、」「〜を、」や見出しの読点も同じように見る。スライド（slides）の見出しには、カギ括弧や引用符の中と数字の区切りの他の読点を残さない（lint の slide_comma。依頼で見出しの形が決まっているときと文書の題はそのままにする）。
- 直したら lint をかけ直す。

原文のファイルを更新する依頼なら、最終稿をそのまま原文の場所に複製する。

## 3. 出力フォーマット

本文のみを返す指定なら、変更理由・質問・注記・確認の記録を付けない。納品物がファイルで返答が別にあるときは返答に欄を付ける。指定がなければ次の形にする。

```markdown
### 書き直した本文

（推敲済みの本文。コードブロックに入れない）

---

### 変えたところ
- 元の表現 → 書き直し後の表現（変更理由）
- （構成や順序を変えた所、つながりの修正、文末をそろえた所（1行にまとめる）、補ったものを最大5点。なければ「なし」と1行）

### 残したAI特有の表現（意味や重みのために残した表現があるときだけ。なければ見出しごと出さない）
- （残した表現と、残した理由）

### 書き手に確かめたい点（本文を決めるのに確認が要るときだけ、最大3点。なければ見出しごと出さない）
- （多いときは、意味や誰が何をするかが変わる所、読み手が動く値や手順、指す先、出典の順番に選び、残りは「- ほかに N か所」。答えで本文が変わらない問いは入れない。「ここに説明が必要です」とペルソナの知らせは3点とは別に数える）

### 確認の記録
- 書き手・読み手・場面: （「書き手: …／読み手: …／場面: …」の形。値ごとに（指定）か（推定）を付け、決めない値は「決めていない」。この形の外の説明は書かない）
- 実行した検査: （lint を実行したら「lint」。実行できなかったときは「実行するコマンド」の節のとおりに書く）
- 見直し候補: （lint の出力の「見直し候補: N件」から「原文 N件 → 最終稿 M件」と書き、「（件数は点数ではない。増減は読みやすさの良し悪しを示さない）」を添える。新規作成では「最終稿 M件」）
```

- エッセイ・小説、紹介記事・宣伝文と判断して表現を残したときは、確認の記録の下に1行のみ書く（「エッセイと判断したので、文の個性を残しました」など）。修正した箇所があっても書き、ペルソナについては書かない。
- lint を実行したことは、読みやすさの合格を示さない。
