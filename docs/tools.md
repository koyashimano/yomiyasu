# 付属ツールの詳しい使い方

README の[付属ツール](../README.md#付属ツール)の節を詳しく書いたものです。出力の読み方、オプション、終了コードをまとめています。

文章の表現と書式を見る `yomiyasu_lint.py` と、lint が読み込む共有モジュール `markdown_visibility.py` を同梱しています。外部ライブラリは不要で、Python の標準ライブラリのみで動きます。Python 3.8 以上の文法で書いており、自動の試験は macOS の Python 3.9.6 と 3.14.5 で動かし、CI では Linux の Python 3.9、3.13、3.14 と Windows の Python 3.12 でも動かしています（Windows を CI に加えたのは 2.1.3 からです。3.8 では確かめていません）。CI では、型注釈と pathlib の検査（ruff と ty）と、Windows の Python 3.9 でのドライブ相対のパスの試験も動かしています。`python3` がない環境では `python` か `py -3` で実行してください。Windows では `py -3 scripts/yomiyasu_lint.py article.md` のように `py -3` で実行します（下の例は `python3` で書いています）。

lint が出すのは見直し候補です。意味が保たれたかと、読み手にとって分かりやすいかは判定しません。候補が0件でも、読みやすいことの証明にはなりません。本ツールは特定の構文を対象とする簡易な検査であり、完全なMarkdownレンダラーでもありません。候補をなくすことを目的に機械的に直すのではなく、元の文や文脈と照らし合わせて判断してください。

## 前後を比べるとき

推敲の前と後を比べるときは、点数ではなく、原文と最終稿に同じ `--doc-type` と `--reader` で lint をかけ、出力の2行目の「見直し候補: N件」を並べてください。スキルも Step 2 で原文に、Step 3 で最終稿に lint をかけ、完了報告の確認の記録に「原文 N件 → 最終稿 M件」と書きます。

- 件数は lint の規則に当たった数です。読みやすさの点数ではありません。増えても減っても、読みやすくなったかどうかは示しません。同梱のコーパスの推敲48組（古いバージョンの yomiyasu の指示で作った出力）では、件数が減った組が7組、同じ組が36組、増えた組が5組でした。確かめるときは、原文と最終稿を読み比べてください。
- スキルは確認の記録の「見直し候補」の行に、件数を「（件数は点数ではない。増減は読みやすさの良し悪しを示さない）」と添えて書きます。新規作成では最終稿の件数のみです。件数の増減を、読みやすくなった根拠としては書きません。
- 1.1.2 までの lint が出していた点数をやめた理由は [点数が出なくなった理由](#点数が出なくなった理由) の節に、JSON に残した `rule_penalty_score` の計算と読み方は [rule_penalty_score の式](#rule_penalty_score-の式) の節に書いています。合否やしきい値には使わず、CI で止めるときは `--fail-on` で候補の中身を見てください。

## 読まないファイル

3.0.0 から、lint は、コマンドラインで名前を渡されたファイルのうち、以下の2つを読みません。終了コード2で止まり、何も書きません。

- 作業フォルダ（コマンドを実行したフォルダ）の外のファイル。シンボリックリンクは、たどった先の場所で見ます。Windows でドライブが違うファイルも外とみなします。大文字と小文字だけ、または日本語の名前の NFC と NFD だけが違うパスは、同じフォルダを指していれば中とみなします（macOS では、Finder などで作ったフォルダの名前が NFD のことがあります）。
- 作業フォルダからの道筋に、名前が点で始まる部分があるファイル（`.env`、`.git/config`、`sub/.secret/x.md` など）。

作業フォルダを読めないとき（実行中に消されたときなど）も、中か外かを決められないので、ファイルは読まずに終了コード2で止まります。

スキルは、lint を許可の確認なしで動かせるように設定しています（SKILL.md の `allowed-tools`）。lint は候補が当たった行をそのまま出力に出します。推敲する文書に紛れ込んだ指示に従って、エージェントが鍵や認証のファイル（`~/.ssh/id_rsa`、`.env` など）をコマンドに渡すと、その中身の一部が出力に出ることがあります。この決まりは、それを防ぐためのものです。

```text
Error opening file ../shared/draft.md: 作業フォルダの外にあるファイルは読みません。このファイルを検査するときは、標準入力から渡してください（ファイルの名前の代わりに - を渡すか、省きます）
```

ほかの場所のファイルは、ファイルの名前の代わりに `-` を渡し、標準入力から渡してください。

```bash
python3 scripts/yomiyasu_lint.py - < ../shared/draft.md
```

道具が自分で探すフォルダは、この決まりに当たりません。用語リストの `.yomiyasu-words/` と references/lists/ は、今までどおり読みます。`--words` で渡す一覧のフォルダにも当てません。読むのは名前の決まった3つのファイル（allow.txt、flag.txt、flag-patterns.txt）だけで、中身は検査の文書に当たった語と、flag.txt でその語に書いた推奨語（80字まで）、語の数と SHA-256 しか出しません。既定の `.yomiyasu-words/` は名前が点で始まり、作業フォルダより上（git の最上位）にあることも多いので、当てると今までの指定が使えなくなります。linked worktree に `.yomiyasu-words/` がないときは、作業フォルダから上へたどって見つけた `.git` ファイルと、その先の git フォルダの commondir、config、config.worktree も読み（中身は出しません）、元の checkout の `.yomiyasu-words/` を探します。

## yomiyasu_lint.py（表現と書式の検査）

1つの文章について、AIの文章に多い表現（不自然な比喩動詞、決まり文句、過剰な太字・箇条書き、絵文字、文末コロン、同一文末の連続など）と、日本語の括弧や句読点に隣接して表示先の規則により太字として表示されない可能性がある書き方（`bold_not_rendered`）を検査します。複数行にまたがる太字やブロック境界（引用、見出し、リスト、表）も考慮して判定します。

2.0.0 からは、通常の出力に点数を出しません。出力の1〜3行目は次の3行で、そのあとに見直し候補を行の順に、規則の ID を付けて並べます。

```text
表現・書式の検査を実行しました。
見直し候補: 3件
この検査では、意味の保持と読者にとっての分かりやすさは判定していません。

内訳: error 0件、warn 3件、info 0件

L3 [WARN] metaphor_verb: 比喩動詞「壊れる」が検出されました。…
```

点数は JSON の `rule_penalty_score` にだけ残しています。規則に当たった箇所が地の文の量に比べてどれだけ多いかを表した目安で、候補がなければ100、あれば1から99です。文章の品質や読みやすさの点数ではないので、合否には使わないでください。推敲の前後を比べるときは、[前後を比べるとき](#前後を比べるとき) の節を見てください。

### 点数が出なくなった理由

1.1.2 の lint は、出力の見出しに「スコア: 90/100」のような点数を出していました。2.0.0 では、この点数を通常の出力から外しました。機能を減らしたのではありません。1.1.2 の規則はすべて残り、`instruction_residue` や `pause_comma` などの規則も足しました。候補は前と同じように1件ずつ出ます（2.0.0 からは行の順に並べ、規則の ID も付けています）。点数は今も `--json` の `rule_penalty_score` で取れます。通常の出力から外した参考値の3行（文字数、太字の頻度、箇条書きの比率）も、JSON の `metrics` にあります。

点数を外したのは、一つの数字が読みやすさの合格点のように見えてしまうからです。点数は決まった規則に当たった箇所を数えただけで、意味が保たれたかも、読み手に伝わるかも見ていません。それでも、95点が100点に上がると文章が良くなったように見えます。逆に、直す前と後で同じ点数だと、読みやすくなったかどうかが分からなくなります（同梱のコーパスでは、4段落を書き直した組が、1.1.2 の点数で前後とも90点でした）。点数が見えていると、点数を上げるための書き換えも起きやすいと考えました。

推敲の前と後を比べるときは、原文と最終稿の「見直し候補: N件」の行を並べ、原文と最終稿を読み比べてください（[前後を比べるとき](#前後を比べるとき)）。件数が減ったことは、読みやすくなった証拠にはなりません。道具で点数を使うときの読み方は、下の「rule_penalty_score の式」の節に書いています。

### rule_penalty_score の式

2.0.0 で、点数を地の文の長さで割る式に変えました。1.1.2 の `score` は件数をそのまま100から引いていたので、同じ文章を2回つなげただけで点数が下がり、長い文書はすぐ0になりました。

候補が0件なら100です。候補があれば、地の文1,000字あたりの重みつきの件数 x を求め、100 × 40 ÷ (40 + x) を四捨五入します。候補があるときは1から99の間に収めるので、0にはなりません。

x の数え方は次のとおりです。地の文は、コードブロック、表、引用、見出し、前置きの設定（frontmatter）、HTML、URL の字を除き、空白も除いた字数です。地の文が1,000字に満たない文書は、1,000字として割ります。行ごとの候補は、error を3、warn を2、info を1として足し、地の文1,000字あたりに直します。ダッシュの3つの規則（`dash_decoration`、`dash_insertion`、`dash_list_ending`）は、候補を1文書3件までしか出しませんが、点数には当たった行をすべて数えます（1行に何か所あっても1件です）。文書全体で1件だけ出る規則は字数で割らず、1,000字の文書で1件当たったのと同じだけ x に足します（`excess_bold` と `excess_list` は2、`bold_label_list` は1）。`negative_parallelism_density` は、同じ箇所を `negative_parallelism` の候補で数えているので足しません。

地の文が1,000字以下の文書に候補が1件だけなら、warn で95点、info で98点、error で93点です。x が40（1,000字あたり warn が20件）なら50点です。1件で下がる幅は一定ではありません。候補が多いほど1件の幅は小さくなり、長い文書では1件増えても点数が変わらないことがあります（地の文6万字の文書では、error、warn、info のどれが1件でも99点です）。

地の文が1,000字以上の文書は、同じ文章を何回つなげても、点数はほとんど変わりません（tests/corpus の163本を1・2・4・8回つなぎ、地の文が1,000字以上になった回どうしで比べると、種類なしと13の種類のどれでも差は2点以内でした）。地の文が1,000字に満たない文書は1,000字として割るので、短い文書どうしでは点数は候補の件数だけで決まり、長いほうが低く出やすくなります。同じ短い文書をくり返すと、地の文が1,000字を越えるまでは点数が下がります（tests/corpus の `human_oga_01.md` は181字で95点、4回つないだ724字で83点、8回つないだ1,448字からは何回つないでも78点です）。

字数で当てるかを決める規則もあります。`excess_bold` と `excess_list` は地の文が300字を超える文書だけ、`short_summary_heading` は2,000字未満の文書だけに出ます。字数が変わると候補そのものが増えたり減ったりするので、点数も動きます（「## まとめ」の見出しが4つある1,044字の文書は91点で、2回つなぐと見出しの候補が出なくなり100点です）。また、候補の密度は文書全体で見るので、長い文書の一部に候補が固まっていても点数にはあまり出ません（warn が20件ある340字の段落は、それだけなら50点、地の文6万字の文書の中に置くと98点です）。どこに何が当たったかは `findings` で見てください。規則ごとの重みは付けていません。人が書いた文の数が、規則ごとの出やすさを決めるには足りないためです。

`--doc-type` を付けると、その種類で外す規則と、種類を指定したときだけ当てる規則（`dialogue_period`、`narrative_density`、`slide_comma`）と、promo と script では出さない `pause_comma`（essay では目的語の「を、」を拾いません）で候補が変わるので、同じ文書でも点数が変わります。2.2.0 から 2.5.0 で足した規則と型（[2.2.0 で足した規則](#220-で足した規則)、[2.3.0 で足した規則](#230-で足した規則)、[2.4.0 で足した直訳語の型](#240-で足した直訳語の型)、[2.4.0 で足したスライドの読点の規則](#240-で足したスライドの読点の規則)、[2.5.0 で足した規則](#250-で足した規則)の `ai_phrase`）の候補は点数を計算する前に除くので、その候補だけの文書は100のままです。種類を変えた結果どうしは比べないでください。バージョンをまたいでも比べないでください。1.1.2 の `score` とは計算が違い、同じ文書でも値が違います。規則を足したバージョンでも値は変わります。JSON の値だけからは点数を計算し直せません。地の文の字数は JSON に出しておらず（`metrics.char_count` は見出しも数えた字数です）、ダッシュの行が4行以上ある文書では `findings` にない行も数えているためです。

CI や道具で使うときは、点数のしきい値で止めず、`--fail-on` の終了コードか、JSON の `counts`（error、warn、info ごとの件数）と `candidate_count`（全部の件数）を使ってください。`rule_penalty_score` は、長さの違う文書の候補の多さを大まかに並べたいときの目安です。

```bash
# Markdownファイルを検査
python3 scripts/yomiyasu_lint.py article.md

# warn か error の候補があれば終了コード1を返す（CIやGitフック用。--strict と同じ）
python3 scripts/yomiyasu_lint.py article.md --fail-on warn

# 文書の種類と読者を指定
python3 scripts/yomiyasu_lint.py slides.md --doc-type slides --reader general

# JSON形式（形式2）で結果を出力
python3 scripts/yomiyasu_lint.py article.md --json
```

- `--strict` か `--fail-on` を付けなければ、候補があっても終了コードは0です。CI で使うときは、点数のしきい値で止めず、候補の中身で止めてください（`--fail-on warn`、太字が表示されない書き方だけなら `--fail-on error`）。止めずに警告として表示するだけの使い方も勧めます。
- 終了コードは、0が検査を最後まで実行して条件に当たらなかったとき、1が `--strict` か `--fail-on` に当たったとき、2が使い方か入力の誤り、3が内部の誤りか、出力先が閉じられて結果を最後まで書けなかったときです。
- `--doc-type` を付けると、その種類で普通な書き方を拾う規則の候補を外し、外した件数を出します（外した候補の中身は、付けずに実行すると見られます）。`--reader` は表示と JSON に残すだけで、候補は変えません。
- 行頭から書いた `<details>` と `</details>` の組の中にある箇条書きは、箇条書きの比率（`excess_list`）に数えません。根拠を `<details>` に畳んだ文書で、過剰な箇条書きの候補が出ないようにするためです。中の箇条書きの行の数は、JSON の `metrics` の `details_list_lines` に出ます。
- JSON の `score` と `is_clean` は、`rule_penalty_score` と `no_rule_findings` に名前を変えました。`rule_penalty_score` は計算も変えたので、1.1.2 の `score` に使っていたしきい値はそのまま使えません（[rule_penalty_score の式](#rule_penalty_score-の式)）。形式は `data.get("format_version", 1)` で見分けられます（[CHANGELOG](../CHANGELOG.md) の「互換性のない変更」）。jq での読み替えの例は [JSON を前のキーの名前で読んでいたとき](#json-を前のキーの名前で読んでいたとき) にあります。

このリンターは、推敲で見落としやすい表現を拾うための補助です。文章をAIが書いたかどうかを判定する道具ではありません。同梱の評価用コーパス（`tests/corpus/`）には、モデルに人の文章らしく書かせた例文が8本あり（`tests/corpus/human/human_doc_*.md`。フォルダの名前は human ですが、人が書いた文ではありません）、8本とも見直し候補は0件でした。候補が少ないことは、人が書いた証拠にはなりません。コーパスの中で人が書いた文章は、作者の記事1本を見出しで8つに分けた抜粋（`human_oga_*.md`）だけです。量が少ないので、人の文章とAIの文章をどれだけ見分けられるかの数値は載せていません。1.1.2 の README に載せた human の16本の数値の訂正は、[CHANGELOG](../CHANGELOG.md) の「訂正」に書いています。

### 2.2.0 で足した規則

- 直訳語は、型で拾うのが主です。用語リスト（[プロジェクトの用語リスト](#プロジェクトの用語リスト)）の役目は、誤った指摘を外すことと、プロジェクトの事情を足すことです。
- 指摘はどれも info です。`--strict` と `--fail-on` の判定にも、`rule_penalty_score` にも入りません。指摘が出ただけでは直さず、文脈を見て、誰が何をどうするかを書き直します。message に置き換え先の語は出しません。
- コードブロックとインラインのコード、URL、引用（`>` の行）、カギ括弧と引用符の中、英数字の識別子は見ません（台詞の句点だけはカギ括弧の中を数えます）。

| 規則 | 見る型 | 当てる種類 |
|---|---|---|
| `calque` | 直訳語。型1は機械やシステムが主語で人や物の動作の動詞（拾う、通る、効く など）、型2は実物の名前の代わりの場所のたとえ（入口、受け口 など）、型3は英語を一語ずつ写した句。1行に1件で、message に型の番号と当たった言い方（置き換え先の語ではありません）が入ります。テストが通る、キャッシュが効く、依存先などの定着した言い方は外します。見出し、表、箇条書きも見ます | すべて |
| `metaphor_label` | 見出しか文書の1行目が、記号を除いて8字以下で、「〜の横」「〜のそば」「〜係」「〜番」で終わるか一語だけで、その語が本文に出てこないもの | essay、promo、script を除く |
| `say_hedge` | 文末の「と言えるでしょう」。名詞のあとの判断（「契約と言えるでしょう」）、「に当たると言えるでしょう」、カギ括弧の中は外します | すべて |
| `thin_evaluation` | 名詞がもともと持つ評価を述語で言い直すだけの文。語の組は `references/lists/thin-evaluation.txt` | すべて |
| `katakana_term` | 意味の薄くなりやすいカタカナ語。語は `references/lists/katakana-terms.txt` | すべて |
| `dialogue_period` | 台詞（「」『』の中、`名前「…」` と `名前：…` の行）が10個以上あり、最後の字が「。」の台詞が5割以上の文書に1件 | script だけ |
| `narrative_density` | 地の文が1,000字以上で、一人称が千字あたり1.0未満、数字と箇条書きの項目が千字あたり8以上の文書に1件 | essay だけ |
| `copy_comma_noun` | 20字以下の文で、「な、」「い、」「た、」「の、」のあとに6字以下の名詞（か名詞＋を）が来て「。」で終わるもの | すべて（promo は文書の2回目から） |
| `bare_verb_chain` | 30字以下の文で、「は」「が」「を」「に」がなく、読点で区切った3つ以上の部分が動詞の終止形か「〜か」で終わり、最後が終止形で「。」になるもの | essay、promo、script、slides を除く |
| `project_term` | 用語リストの flag.txt の語と、flag-patterns.txt のパターン（3.0.0）。1行に1件で、message にその行の語とパターンの名前が入り、flag.txt に推奨語があれば末尾に添えます | すべて |

### 2.3.0 で足した規則

`renyo_noun`（info）は、他動詞の連用形を1語だけ名詞にした語を「の」で受ける形（「結果の確かめ」「二つの案の比べ」）を指摘する規則です。この形の語は名詞としての自立性が弱く、目的語を「の」で受ける形では使いにくい、という日本語の文法の研究（蔡盛植「日本語動詞連用形への構文論的アプローチ」日本研究 第21集、2014）にもとづいています。漢語を避けて和語で書くと出やすい形です。

- 当てるのは、`references/lists/renyo-nouns.txt` の語（確かめ、直し、比べ、測り、補い、決め、選び、集め など）が「の」のすぐあとに来て、そのあとに助詞（が、を、は、に、で、も、と、から、など、だけ など）か、句読点か、閉じ括弧か、行の終わりが続く所です。指示語の「その」「この」で受ける形（「その確かめは」）にも当てます。1行に1件で、message に当たった言い方（「の確かめ」など。置き換え先の語ではありません）が入ります。見出し、表、箇条書きも見ます。当てる種類はすべてです。
- 当てないもの: 名詞とくっつけた複合語（資金集め、手直し）、複合動詞から来た語（見直し、組み合わせ、洗い出し）、「お」「ご」を付けた形（お選び）、別の意味で名詞として定着した語（住民票の写し、合格の知らせ、詰めが甘い、法律の定め、警察の調べ など。一覧に入れていません）、動詞に続く形（入れやすい、確かめにくい、決めがたい）、「生活の足しになる」「試しに」の「に」、前に「の」がない形（「確かめの道具」）、語のあとに「か」「だ」が続く形（「結果の確かめか」「案の比べだ」）。カギ括弧と引用符の中、引用、コード、HTML の行、英数字の識別子も見ません。
- 推敲では、目的語と動詞の文に戻すか（結果を確かめる）、定着した漢語の名詞にします（結果の確認）。ほかの和語の連用形名詞に替えるだけでは済ませません（SKILL.md「直訳語、漢語の詰まり、連用形名詞」）。
- 人のニュース記事（livedoor ニュースコーパス、7,367本、約900万字）、Claude に素で書かせた日本語の48本（約10万字）、同梱の tests/corpus の163本（3.0.0 の時点の181本でも同じ）では、指摘は0件でした。指摘は info で、`--strict` と `--fail-on` の判定にも、`rule_penalty_score` にも入りません。
- プロジェクトで定着している語は、用語リストの `allow.txt` に「の」を付けずに語だけ（確かめ）を書くと外れます。

`references/lists/` の katakana-terms.txt、thin-evaluation.txt、renyo-nouns.txt がないか読めないときは、組み込みの一覧で同じ候補を出します。

### 2.4.0 で足した直訳語の型

`calque` に型4を足しました。英語の短い術語に当てた漢字1字の名詞（「今回の版」の version、「一覧の頭」の head、「lint の印」の mark）に、info の指摘を出します。message には「型4: 英語の短い術語に当てた漢字1字の名詞」と、当たった字（版、印、頭）が入ります。

- 前の語の修飾を受けて名詞として使う「版」（「今回の版」「直した版」「同じ版の」）と、「版ごと」「版の文字列」「版をまたいで」の形に当てます。文に出版物の語（新聞、雑誌、映画、吹き替え など）があれば当てません。同じ行に `translated_term`（warn）の候補があれば、型4の「版」は重ねません。
- 1字で使う「印」には、同じ文に検査や推敲の語（lint、diff、検査、検証、推敲、ログ など）があるときだけ当てます。「×印」「目印」「焼き印」は当てません。同じ文に検査や推敲の語があると、「地図の印」のような文字どおりの使い方にも指摘が出ることがあります。
- 行、一覧、出力、ログ、ファイル、PR などの位置を言う「頭」（「一覧の頭」「出力の頭」）と、「頭の2行」のような形に当てます。「頭が痛い」「曲の頭」のような体や慣用の「頭」は当てません。
- 推敲ではその分野で使う呼び名（バージョン、先頭、指摘）で書きます。何を指すかが原文や資料から決まらなければ、本文を残して書き手に確かめます（`references/calques.md` 4章）。

### 2.4.0 で足したスライドの読点の規則

3.4.0 からの `#` の見出し（文書の題を除く）は、下の「3.4.0 で変えたスライドの見出しの読点」を見てください。

`slide_comma`（info）は、`--doc-type slides` のときだけ、見出しと1行の箇条の、間を作るだけの読点を指摘する規則です。見出しと箇条は一目で読むので、地の文なら残す読点でも外す候補にします。1行に1件で、message に当たった言い方が入ります。

- 見るのは、1行で終わる60字以下の見出し、箇条書き、段落の行です。続きの行がある項目と、複数行の段落の行は見ません。行頭の箇条の印（入れ子も）、「・」「①」「(1)」のような印、【】、「結論：」のようなラベルは外してから文頭を決めます。
- 当てるのは、文頭のつなぎの語（だから、それでも、そこで、結局、まず など）のあと、文頭の決まった「〜ば」（振り返れば、数字で言えば、言われてみれば など）のあと、文頭の6字以上の時や場面の句（その日のうちに、会議が終わるまでに など）のあと、文頭から15字以内の主題（〜では、〜は、〜も）のあと、文頭から10字以内の主語（名詞＋が）のあと、目的語の「を」のあとの読点です。
- 当てないもの: 逆接（のに、ても、けれども、ながらも、述語＋が）、条件（なら、たら、「〜ときは」「〜場合は」、「上司に言えば」のような「〜ば」）、理由や目的（ので、ために、ためには、するには）、名詞の並び（A、B、C と「Aを、Bを、」）、「その夜、」「翌朝、」のような短い時の句、主題のあとに別の主語が続く所（会議では、担当者が。主語が「〜がある」「〜がない」「〜が多い」のように、あるかないかや数を言う文の主語のときは当てます）と、主題のあとに読点で区切った並びが続く形（〜のは、A、B、C）、長い主語のあとの読点。カギ括弧と引用符の中、引用（`>` の行）、コード、リンクの URL、英数字の識別子は見ません。同じ行に `pause_comma` が出ているときは、主題と主語の読点を重ねて出しません。
- 推敲では、外しても読み違えない読点だけを外します（`references/doc-types/slides.md` 2章）。点数（`rule_penalty_score`）には入りません。ほかの種類では出しません。

### 3.0.0 で足した直訳語の型と、前提の比喩の形

- `calque` の型4に「枝」「題」「罫」を足しました。「枝」は前後に漢字のない1字の「枝」で、同じ文に git の語（git、Git、GitHub、main、master、rebase、worktree、マージ、プルリク。マージンは数えません）があるとき、「題」は「PR の題」「プルリク（エスト）の題」「コミットの題」「issue の題」「イシューの題」「README の題」の形だけ（自己PR、商品PR のような前に漢字かカタカナが付く PR と、「題名」は当てません）、「罫」は前後に漢字のない1字の「罫」で、同じ文にスタイルの語（CSS、border、px、HTML）があるときに当てます。「飾り罫」には当てません。git の語がない文の「木の枝」、「作文の題」、スタイルの語がない文の「便箋の罫」や、組版や表計算の「表の罫」には当てません（同じ文にスタイルの語があれば「表の罫」にも当てます）。

### 3.2.0 で足した規則と変えた規則

- `pause_comma`（3.2.0 のときは `--doc-type` を指定したときだけ。3.3.0 からは種類を指定しないときも指摘を出します）は、読点のあとに別の主語が来る所に当てません。3.2.0 から、この判定で動詞の中の「が」（つながります、切り替わりながら、つながって）を主語に数えません。動詞の中の「が」とみなすのは、直前が平仮名で、すぐあとが「ら」「り」「る」「れ」「ろ」「っ」の「が」です。「小さな工夫が、やがて大きな変化につながります。」の読点に指摘が出るようになります。直前が漢字の「が」（広がる）は今までどおり主語に数えるので、「毎日の練習が、少しずつ自信に広がっていきます。」には出ません。

- `pause_comma` で、文頭の場面の枠（「この記事では、」「この画面には、」）のあとの読点を拾った行のうち、その読点から次の読点か文末までが空白を除いて20字以上ある行には、今までどおり指摘を出したうえで、message の最後に「文頭の場面の枠（「この記事では、」など）のあとで文が長く、外すと区切りが見えにくくなるときは、残してかまいません。」を足します。当てるのは「では、」「には、」だけです。ほかの行の message と、件数、行、severity、snippet は変えていません。

- `ai_phrase` に「多岐にわたる」「が求められている」を足しました（上の 2.5.0 の表）。2.5.0 からの7つの形の当たり方は、同じ行に新しい語があっても変わりません。
- `slop_vocabulary` で、すぐあとが「の中で動」「内で動」「に組み込」「を制御」「の制御」の「装置」を、文字どおりの機器とみなして拾いません（装置に組み込む場合）。比喩の「増幅装置だ」「記憶を呼び起こす装置として」と、「装置の中で特別な位置を占める」は今までどおり拾います。

### 3.4.0 で変えたスライドの見出しの読点

- `--doc-type slides` の `slide_comma` は `#` で始まる見出し（文書の題を除く）の読点を、形を問わず全部候補に出します。見ないのは、カギ括弧や引用符の中（「」『』“” "" ‘’）、コード、リンクの文字と URL、英数字の識別子と、数字の区切り（1,000、１２，０００）です。半角の「,」は読点に数えません。数字の区切りでない全角の「，」は読点に数えます。60字を超える見出しも見ます。1行に1件で、message に当たった言い方が並びます。当たった言い方がカギ括弧などの中の読点を含むときは、その所のあとから切り出して頭に「…」を付けます。
- 文書の題は、原稿の最初の見出しが `# ` の見出しで、`# ` の見出しがそれ1つだけのときの、その見出しです。題は 2.4.0 からの型で見ます。Marp のように `# ` の見出しが2つ以上ある原稿には題がなく、どの `# ` の見出しにも全部の読点を出します。引用（`>` の行）の中の見出しは数えません。
- 1行の箇条と、`#` で始まらない見出しの行（下線の見出し。箇条のすぐ下の `---` で見出しになった行も）は、2.4.0 からの型のままです。ほかの種類では出しません。点数（`rule_penalty_score`）には入りません。
- 限界: 下線の見出し（setext）と、リンクの文字や `[ ]` の中の読点は、全部の読点を出す対象にしません。〝〟と全角の＂＂は引用符に数えないので、その中の読点も候補に出ます（〝はい、いいえ〟で答える）。数の並び（2、3日）の「、」は候補に出ます（「2〜3日」と書けば出ません）。依頼で見出しの形が決まっていても候補は出ますが、推敲ではその形を保ちます（`references/doc-types/slides.md`）。
- message の当たった言い方には次の限りがあります。候補に出る見出しの行は変わりません。同じ言い方の読点が2つあっても1つだけ並べます（確認、確認、また確認 では「確認、」が1つ）。引用の中に読点があり、引用のすぐあとにも読点があるときは「…、」とだけ出します（「速く、正しく」、そして安く）。時刻や比の「:」「：」のあとから切り出すことがあります（会議は12:30、場所は本社 では「30、」）。引用の中の数字の区切りの「，」は、引用の中の読点と同じく扱います（「１２，０００円」より、安い では「…より、」）。3.4.1 から、数字の区切りの「，」のあとからは切り出しません（１２，０００件、達成 では「１２，０００件、」。3.4.0 は「０００件、」でした）。

### プロジェクトの用語リスト

git の最上位に `.yomiyasu-words/` フォルダを置き、2つのファイルに1行に1語ずつ書きます（3.0.0 から、正規表現を書く3つ目のファイル `flag-patterns.txt` も置けます）。リポジトリに入れてチームで共有する前提のファイルです。

- `allow.txt`: 直さない語（その分野で定着した言い方）。`ai_phrase`、`calque`、`metaphor_label`、`katakana_term`、`project_term`、`renyo_noun` と、`metaphor_verb`、`translated_term`、`slop_vocabulary` の候補のうち、当たった語が一覧の語と同じものを外します。`ai_phrase`、`calque`、`katakana_term`、`project_term`、`renyo_noun` は1行に1件で行の語を並べるので、許した語だけを除き、ほかの語が残れば候補を残します。外した件数（候補ごと外したもの）は出力と JSON に出ます。
- `flag.txt`: 指摘を出して見直す語（その分野で見直したい言い方）。`project_term`（info）の指摘を出します。扱いはほかの新しい指摘と同じで、文脈を見て書き直すかを決めます。3.0.0 から、漢字と仮名を両方含む語（根の、の木）は、漢字の端の前後に漢字が続く所（大根の、の木構造）では数えません。漢字だけの語と仮名だけの語は、今までどおり語の一部にも当たります。語の一部にも当てたいときは、flag-patterns.txt に書いてください。
  - 1行に `使わない語<TAB>推奨語` とも書けます。`<TAB>` は実際のタブ文字です。最初の TAB の左だけを探し、指摘の末尾に「推奨語: 指紋 → fingerprint。」のように添えます。TAB のない行は今までどおりです。行の前後の空白と TAB を除いてから分けるので、TAB で字下げした行も今までどおり読みます。使わない語と推奨語の前後の空白も除き、右が空なら推奨語は出しません。桁をそろえるために TAB を続けて書いても読めます。推奨語は替える名前の出典にできます（[calques.md 4章](../references/calques.md#4-書き直し方)）。
  - 推奨語は80字までです。推奨語の中に TAB がある行（`使わない語<TAB>推奨語<TAB>メモ` のような3列の行）と、推奨語が80字を超える行があると、lint は終了コード2で止め、ファイルの名前と行番号を出します。同じ使わない語に違う推奨語を書いた行が2つあると、あとの行の推奨語を使います。エディタが TAB を空白に置き換えた行は、空白ごと1語として読むので、その語の指摘も推奨語も出なくなります（読めたかどうかは、指摘の末尾に「推奨語:」が出るかで確かめられます）。
  - 推奨語が使わない語を含む組（`サーバ<TAB>サーバー`、`問い合わせ<TAB>お問い合わせ`）では、もう推奨語で書いてある所は数えません。英数字で始まるか終わる推奨語は、その端が語の境目にある所だけを推奨語とみなします（`user<TAB>end user` と書いても、「backend user」の user は数えます）。日本語の字の端では語の境目を見分けないので、前後の字と合わせて推奨語と同じ並びになる所（`問い合わせ<TAB>お問い合わせ` での「なお問い合わせ」）も数えません。推奨語が使わない語と同じ行（`サーバ<TAB>サーバ`）は、推奨語のない行として読みます。推奨語のない行は、今までどおり語の一部にも当たります。
- `flag-patterns.txt`（3.0.0）: 1行に `名前<TAB>正規表現` を書きます。当たった行に `project_term`（info）の指摘を出し、message にはパターンの名前が入ります（パターンだけなら「用語リスト（flag-patterns.txt）の言葉（名前）」、flag.txt の語と同じ行なら「用語リスト（flag.txt、flag-patterns.txt）の言葉（…）」）。見る所は flag.txt と同じです。`allow.txt` にパターンの名前を書くとそのパターンの指摘が外れ、当たった文字列を書くと、その行のそのパターンの当たりがどれも許した文字列のときだけ外れます。
  - 名前は40字まで、正規表現は200字まで、パターンは500個までです。正規表現の前後の半角の空白とタブは除きます（全角の空白は正規表現の字として残ります。半角の空白で終わる正規表現は、最後の空白を `[ ]` と書きます）。
  - 使える書き方は、字、`.`、`[...]`、`\d \D \w \W \s \S \b \B \A \Z \t \n`、記号の前の `\`、`^`、`$`、`|`、`(?:)`、`(?=)`、`(?!)`、`(?<=)`、`(?<!)` と、繰り返しの `?`、`{m}`、`{m,n}`（n は30まで。`{m,n}` は1字の要素にだけ付けられ、グループに付けられるのは `?` だけで、先読み・後読みと `^`、`$`、`\b` には `?` も付けられません。どれも、あとに最短一致の `?` を付けられます）です。
  - 上限のない繰り返し（`*`、`+`、`{m,}`）、`{,n}`、キャプチャグループ `( )`、名前付きグループ、後方参照、インラインフラグ（`(?i)` など）、コメント、条件付きのグループ、アトミックグループと強欲な量指定子（Python 3.9 で使えない）、`\z`（Python 3.14 から）、`[ ]` の中の `[` と `--`、`&&`、`~~`、`||`（警告が出る）は使えません。
  - 1つのパターンで、繰り返しの幅と選択肢の数の積は512まで、全パターンの合計も512までです（かかる時間はこの合計にほぼ比例します）。どの選択肢にも、`?` や繰り返し、先読み・後読みの外に必ず当たる字が要ります。`.`、`[...]`、`\d` のような字の集まりと、選択肢のあるグループ（`(?:鍵|錠)`）の中の字は数えないので、`[鍵錠]` や `(?:鍵|錠)` だけのパターンは使えません（`鍵|錠` と書きます）。その字がない行にはパターンを当てません。後読みは長さが決まっている必要があります。
  - 使えない行があると、lint は終了コード2で止め、ファイルの名前と行番号を出します。「鍵」に当てて「公開鍵」の「鍵」には当てたくないときは、flag.txt に「鍵」を書かずに（漢字だけの語は熟語の中にも当たるので）、flag-patterns.txt に `(?<!公開)鍵` のように後読みで書きます。lint の `--help` は、`--words` の説明と終了コード2の一覧で flag-patterns.txt に触れています。

lint は以下の順序で探します。

1. `--words フォルダ` を指定したときは、そのフォルダ（ないフォルダを指定すると終了コード2）。
2. 作業ディレクトリから上へたどり、`.git`（フォルダでもファイルでもよい）があるフォルダの `.yomiyasu-words/`。入れ子のリポジトリでは近いほうの最上位です。linked worktree にこのフォルダがなければ、`.git` ファイルの gitdir とその先の commondir をたどって、元の checkout の `.yomiyasu-words/` を探します。元の checkout は、共有の git フォルダの config（`core.worktree` を移した config.worktree も読みます）の `core.worktree` が指す先（submodule から作った worktree）か、共有の git フォルダの名前が `.git` で bare でないときの、その親のフォルダです。bare リポジトリから作った worktree では探しません。`--separate-git-dir` で git フォルダを別の場所に置いたリポジトリから作った worktree でも、git フォルダの名前が `.git` でなければ探しません（名前が `.git` の置き場では、その親を元の checkout とみなします）。config は、git が書く形（1行に `キー = 値`）で読みます。手で書き足した形（行末のコメント、値のない `bare`、`[include]` の先の値など）は、git と同じには読めません。config を読めないときは、`core.worktree` も `bare` も書いてないものとして扱います。worktree 自身にフォルダがあれば、そちらだけを読み、元の checkout の一覧とは混ぜません。
3. git の外では、作業ディレクトリの `.yomiyasu-words/`。

`--no-words` を付けると、一覧を探しも読みもしません（`--words` と一緒には使えません）。フォルダがないときと、フォルダに allow.txt、flag.txt、flag-patterns.txt のどれもないときは、一覧なしとして動きます。一覧がないときの出力は、2.2.0 から 2.5.0 で足した規則と型の候補、3.0.0 で足した直訳語の型4の字と型5の候補と、`metaphor_verb` の前提の比喩の広げた形と指摘の文、2.5.0 で `pause_comma` に足した短い目的語の「を、」と外した掛かり先の読点、2.5.0 で比喩の「効く」の `metaphor_verb` がソフトウェアの語の近くでも出るようになったこと、2.4.0 で変えた出力の言葉（「太字の印」を「太字の記号」にしたなど）、3.2.0 で足した規則と変えた規則（`pause_comma`、`ai_phrase`、`slop_vocabulary`）のほかは 2.1.3 と同じです。

ファイルは UTF-8 のテキストで、`#` で始まる行と空の行は読み飛ばします。BOM と CRLF の改行も読めます。UTF-8 でないファイルと、1万行を超えるファイルがあると、終了コード2で止め、ファイルの名前と行番号を出します。

一覧を使ったときだけ、JSON の `context` に `words` が入ります。中身は、`path`（フォルダの場所）、`allow_lines` と `flag_lines`（語の数）、`allow_sha256` と `flag_sha256`（ファイルの中身の SHA-256。ファイルがないほうは null で、行数は0）です。lint では、これに `allow_removed`（規則ごとの外した件数）が加わります。人が読む出力には「用語リスト: <場所>（allow N語、flag N語）」の行が出ます。flag-patterns.txt があるときだけ、`flag_sha256` のあとに `flag_patterns_lines`（パターンの数）と `flag_patterns_sha256` が加わり、人が読む出力の行の括弧は「（allow N語、flag N語、flag-patterns N行）」の形です。

### JSON を前のキーの名前で読んでいたとき

1.1.2 までの lint の `--json` の出力を読むスクリプトがあれば、2.0.0 からはキーの名前を読み替えてください。前の名前のキーは残していないので、`jq .score` と `jq .is_clean` は `null` を返します。`jq -e .is_clean` のように jq の終了コードで判定していた CI は、候補があってもなくても失敗します。

| 1.1.2 まで | 2.0.0 から | 中身 |
|---|---|---|
| `score` | `rule_penalty_score` | 規則に当たった候補の多さの目安です。計算を変えたので、前のしきい値はそのまま使えません（[rule_penalty_score の式](#rule_penalty_score-の式)） |
| `is_clean` | `no_rule_findings` | 候補が1件もなければ true です。`candidate_count` が0のときと同じです |

`format_version` は 2.0.0 からの JSON にあり、値は2です。1.1.2 までの JSON にはこのキーがないので、ないときは1とみなしてください。

```bash
# 2.0.0 からの名前で読む
python3 scripts/yomiyasu_lint.py article.md --json | jq '.rule_penalty_score'
python3 scripts/yomiyasu_lint.py article.md --json | jq '.no_rule_findings'

# 形式を見分ける（2.0.0 からは2、1.1.2 までは1）
python3 scripts/yomiyasu_lint.py article.md --json | jq '.format_version // 1'

# 1.1.2 と 2.0.0 のどちらの JSON でも読む
python3 scripts/yomiyasu_lint.py article.md --json | jq 'if (.format_version // 1) >= 2 then .rule_penalty_score else .score end'
python3 scripts/yomiyasu_lint.py article.md --json | jq 'if (.format_version // 1) >= 2 then .no_rule_findings else .is_clean end'
```

候補の有無を `jq '.no_rule_findings // .is_clean'` と書くと、2.0.0 からの JSON で候補がある文書では `null` になります。jq の `//` は false も値がないものとして扱い、右の `.is_clean` を読むためです。上の例のように `format_version` で分けてください。

CI で止めるときは、点数のしきい値の代わりに `--fail-on` を使ってください。JSON で判定したいときは、`counts` の件数を使えます。

```bash
# warn か error の候補があれば終了コード1（jq は要りません）
python3 scripts/yomiyasu_lint.py article.md --fail-on warn

# 同じ判定を JSON で行う（warn か error の候補があれば jq の終了コードが1）
python3 scripts/yomiyasu_lint.py article.md --json | jq -e '.counts.error + .counts.warn == 0'
```

この節の jq の例は 2.0.1 の lint の出力に jq 1.7.1 をかけて確かめました。どちらの JSON でも読む2つの例と `//` の例は、1.1.2 の lint の出力にもかけて確かめています。
