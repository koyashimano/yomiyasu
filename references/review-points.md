# lint の出力の見方と目視の点検

SKILL.md の Step 2 の1と Step 3 で lint の指摘を見るときに読む。Python を実行できないときは4章の目視の点検に従う。

候補は修正の指示ではなく、文脈を読み直す箇所。候補を消すことのみを目的に言い換えを繰り返さない。候補が出ないことも、読みやすいことの証明ではない。lint は点数を出さない。候補の数を品質の合格点として扱わない。

## 1. 出力の冒頭の行

- 1行目は検査を実行したことの知らせ。
- 2行目は「見直し候補: N件」。原文と最終稿の件数を、確認の記録の「見直し候補」の行に「原文 N件 → 最終稿 M件」と書く。件数は点数ではなく、増減は読みやすさの良し悪しを示さない。
- `--doc-type` か `--reader` を付けたときは、種類と読者と、外した規則の件数の行が続く。
- 候補があれば「内訳: error N件、warn N件、info N件」の行の後に、1件ずつ行番号、重さ、規則の名前、説明、該当した行が出る。

## 2. 指摘ごとの見方


- 文脈に合う専門用語や事実の記述は、無理に言い換えない。「大事です」のような評価を担う言葉や、主張に必要な否定（AではなくB）は残す。
- 太字にならない書き方: 元の太字が表示されるかを確認し、すでに表示される書き方なら変えない。修正するときは、太字の範囲や前後の文が崩れないかを確認し、不確かな案はそのまま適用せずに目で整える。意味は変わらないので「変えたところ」には書かない。
- `--doc-type` を付けたときは、その種類で普通な書き方を検出する規則の候補を lint が除外し、除外した件数のみを出す（中身は `--doc-type` を付けずに実行すると見られる）。除外されるのは種類の表の範囲のみで、他の型は SKILL.md 1章のとおりに確認する。
- 過剰な箇条書きの候補（excess_list）は、行頭から書いた `<details>` と `</details>` の間の箇条書きを、比率の分子にも分母にも数えない（中に多く折りたたんでも、外の箇条書きの比率は薄まらない。中に箇条書きがあれば、候補に「（<details> の中の箇条書きN行は数えていません）」と添える）。折りたたんだ中の箇条書きも、論理を分断していないかは SKILL.md「構成と順序」の箇条書きの項目のとおりに読む。
- 同じ文末が続くという候補は、読みにくさを見直すきっかけにとどめる。AIの文の目印として扱わず、語尾を散らすために文の働きや時制を変えない（gemini-syntax.md 原則8）。
- 2.2.0 で追加した info の指摘（calque、metaphor_label、say_hedge、thin_evaluation、katakana_term、dialogue_period、narrative_density、copy_comma_noun、bare_verb_chain、project_term）は、修正の合図ではなく、文脈を読み直すための候補。指摘が出たことのみを理由に修正せず、言葉を残すこともある。修正するときは、誰が何をどうするかを文として書き直す（SKILL.md Step 2）。点数（rule_penalty_score）には入らない。

  - 用語リスト（`.yomiyasu-words/`）を使ったときは、allow.txt の言葉で除外した件数が出る。除外された候補の言葉は、そのプロジェクトで定着した表現として修正しない。

## 3. 候補に出なくても確かめること

- 文書の用件と段落: 個々の文の時制を分けたり語尾の種類を数えたりせず、読み手の立場で段落を通読する。用件を果たしているか、誰が何をするかが自然に伝わるか（語尾の種類の数やばらつきは基準にしない）。変更報告では、どの文から書き手が何をどう改めたと読み取れるか。仕組みの説明や現在の方針・動作が用件ならその内容を残し、段落の目的に合う文末や正当な時制の混在は保つ。
- 構造: 用件や結論が冒頭で伝わるか。誰が何をどの条件で行うか、修飾先、例外・否定・限定・数量、並列や出来事の順序を追うときに、読み戻る箇所が減ったか。助詞や語順を変えた箇所では、対象となる人や場面、条件が揃えば行うことと、その条件のときのみ行うことの区別が保たれているか。
- 本文内の反復: 同じ段落で一つの問題や結果を長く言い直していないか。指示語で受けられる重複は整理し、複数の対象を区別するための再掲は残す。種類が promo のときの同じ褒め言葉の繰り返しは、反復として整理せずに残す（doc-types/promo.md）。
- 名詞と説明文: 本文と「変えたところ」などの説明の欄で、言葉が指す役割に合っているか。元にない信頼性・唯一性・約束を追加していないか。

## 4. 目視の点検（Python を実行できないとき）

原文と最終稿（新規作成では資料と最終稿）を以下の観点で読む。確認の記録の「実行した検査」には「なし（Python がないため lint を実行しなかった。観点を目で点検した）」と書く。

- 文書全体の用件が冒頭で伝わるか、段落の目的と順序、変更報告で改定の内容が読み取れるか、文末が立場に合うか
- だれが何をするか（主語、目的語、使役の相手）
- SKILL.md 1章の型（比喩動詞、擬人化、否定対比、大げさな名詞、前置き、締めの言い直し、直訳語、詰まった漢語）
- 段落と箇条書きの使い分け、接続語と指示語の繋がり
- 間を作るのみの読点、太字のラベルとコロン、絵文字やダッシュのような装飾記号
- 太字が表示される書き方か
