# 文書の種類と読者

SKILL.md 2章 Step 1 の種類と読者の決め方の細部。種類か読者の推定に迷うとき、informed か general を指定されたとき、「ここに説明が必要です」を書くときに読む。書き手と読み手との関係は `persona.md`。

どの種類と読者でも、意味を保つこと（SKILL.md「意味の保持」）と追加しないこと（「情報を追加しない」）は同じ。

## 1. 種類の手がかり

| 種類 | 依頼の手がかり | 本文の手がかり |
|---|---|---|
| pr | PR、プルリクエスト、変更の説明 | 概要、変更点、テスト、確認したことの見出し。Issue の番号、ファイル名、ブランチ名 |
| article | 技術ブログ、Zenn、Qiita、記事 | 導入の段落、コードブロックとその説明、「本記事では」 |
| incident | 障害、インシデント、ふりかえり | 発生日時、影響範囲、原因、暫定対応、再発防止。時刻つきの経過 |
| proposal | 提案、企画、稟議 | 背景、目的、提案、費用、期待する効果。判断を求める文 |
| minutes | 議事録、会議のメモ | 日時、出席者、議題、決定事項、宿題の欄 |
| manual | 手順書、マニュアル、使い方 | 番号つきの手順、「〜してください」の連続、前提条件、注意 |
| slides | スライド、発表資料、登壇 | `---` のページの区切り、Marp などのフロントマター、ページごとの短い見出しと箇条書き |
| essay | note、エッセイ、日記、小説 | 一人称の語り、体験と気持ち、会話文と地の文 |
| formal | 規程、契約書、公用文、仕様書、約款 | 第1条などの条の番号、「〜するものとする」、甲と乙、定義の条、施行日や契約の期間 |
| promo | 紹介記事、宣伝文、おすすめ記事、商品やお店の紹介 | 「〇選」「おすすめ」「イチオシ」の見出し、ランキングや一覧の形、価格や購入先の案内 |
| mail | メール、チャット、Slack の投稿、返信、DM | 宛名（〇〇様、〇〇さん）、「お世話になっております」のような挨拶、署名、「よろしくお願いいたします」で終わる形 |
| paper | 論文、学会の予稿、卒業論文、研究レポート、調査報告 | 「本研究では」「先行研究」、引用の書き方（[1]、(山田 2020)）、「考察」「結論」の見出し |
| script | 漫画のネーム、シナリオ、脚本、台本、ドラマや劇の台詞 | `名前「…」` か `名前：…` の台詞の行、コマやシーンの番号、（ ）やト書きの行、SE や M の指示 |

- どれにも当たらない文書（全社向けのお知らせ、週次報告、チャットの共有文、リリースノート）は種類を決めない。
- 商品やお店を勧める記事は、note や個人のブログに載せる個人の記事でも promo にする（essay の手がかりにも当たるが、勧める記事なら promo を主な種類とする）。
- 仕様書は formal にする（読み手が規則として従う文書）。使い方を手順で示す文書は manual。1つの文書が2つの種類にまたがるとき（台本つきのスライド、提案を含む議事録）は、主な種類が1つに決まればそれにし、決まらなければ決めない。
- 文書の立場（勧め、決まり、説明）は種類とは別に決める。種類から立場を決めない。

## 2. 読者の手がかり

- 依頼の宛先（「全社員向け」は general、「チームの開発者に」「レビュアーに」は expert、「上長に」は informed）と、掲載先（社内 Wiki、公開のブログ、顧客向けのお知らせ）。
- 本文が略語を説明なしで使っていることは弱い手がかりにとどめる。書き手の想定を示すのみで、読む人が専門家とは限らない。
- 種類から決める既定の読者は、pr と minutes の expert（レビューする開発者と、会議の出席者）のみ。
- 関係を指定されたときは persona.md 2章の目安で段階を決めてよい（推定と書く）。関係を推定したにとどまるときは、この章の手がかりのみで決める。

## 3. 推定で進めてよいとき

- 種類: (a) 掲載先か宛先が1つの種類を示し、本文に他の種類の手がかりがない。(b) 本文に1つの種類の手がかりが2つ以上あり、他の種類の手がかりがない。ただし minutes と slides は、本文の形の手がかり（出席者と議題の欄、`---` のページの区切りか Marp の設定）が少なくとも1つ必要。
- 読者: (a) 依頼か宛先が読者を示す。(b) 種類が pr か minutes で、依頼と本文に expert と食い違う手がかりがない。
- どれにも当たらなければ自信がないとする。掲載先（note に載せる、社内 Wiki に置く）から決めたものも、指定ではなく推定とする。
- 指定と本文の形が食い違うとき（「議事録です」と言われたが本文は提案書の形）は指定に従い、本文を種類の形に組み替えない。

## 4. 確かめるか、決めずに進むか

1. 決め方で修正方法が変わらないなら、確認せず、決めもしない。種類では、候補の種類どうしで除外する規則と普通な書き方が同じときがこれに当たる（提案書か技術記事か迷うが、どちらも除外する規則がない）。読者では、説明のない分野の用語、略語、社内の呼び名がないときがこれに当たる。
2. 修正方法が変わり、問い返せるなら、書き直す前に1回のみ確認する。
3. 次の場面では問い返さず、決めずに進む。
   - 本文のみを返す指定がある。
   - 他のスキルの途中で呼ばれた。
   - 利用者が「確かめずに」「おまかせで」「質問しないで」と頼んだ。
   - 非対話の実行（`claude -p`、`codex exec`、CI、フック。依頼に返事を待てない旨があるか、ホストから分かるとき。分からなければ問い返せるものとする）。
   - 同じ依頼の中ですでに1回確認した（複数の原稿をまとめて修正する依頼でも1回のみ）。

問いは種類と読者を1つにまとめ、番号の選択肢と「おまかせ」を出す。各選択肢に、選ぶと修正方法の何が変わるかを短く添える。推定の候補を先に並べるが、どれも勧めない。原稿の評価や修正方法の提案を混ぜない。

```text
書き直す前に1つだけ確かめます。番号で答えてください。
文書の種類: 1. スライド（短い箇条書きと見出しをそのまま残します） 2. 技術記事 3. おまかせ
読み手: 1. 同じ分野の専門家（用語を残します） 2. 分野は違うが技術に詳しい人 3. 専門知識のない人（説明が要る所をお返しします） 4. おまかせ
```

- 番号の答えは指定として扱う。
- 「おまかせ」、分からない、答えずに別の依頼を出したときは、その軸を決めず、もう確認しない。
- 選択肢にない説明（「経理の人が読む」）は相手と関係の指定として受け取り、persona.md 3章で決める。段階はこの章と2章で決める。決まらなければ決めない。
- 関係を問うときは persona.md 3章の行を追加し、1つの問いにまとめる。

## 5. 決めないとき

- 種類を決めない: doc-types のファイル（SKILL.md 2章 Step 1）を使わない。分野が分かれば domains のファイルを読む。lint に `--doc-type` を付けない（lint は全ての規則を適用する）。
- 読者を決めない: 用語は SKILL.md「専門用語と名称の扱い」のとおりに扱う。説明が必要な所は返さない。lint に `--reader` を付けない。
- どちらも、SKILL.md 1章の規則のみで修正する。

## 6. 推定のときに使う調整の範囲

| 調整 | 指定（確認した答えを含む） | 推定 |
|---|---|---|
| 種類で除外する規則と、その種類で普通な書き方を修正しないこと | 使う | 使う |
| 用語を残し、説明を追加しない（expert） | 使う | 使う |
| 識別子が主語の文を修正しない（expert、informed） | 使う | 使う |
| 説明が必要な所を返す（informed、general） | 使う | 使う |
| 用語を言い換えるか、原文と資料の説明を添える（informed、general） | 使う（8章の条件のとき） | 使わない。言葉を残して説明が必要な所に出す |
| 文を分ける範囲を広げる（general） | 使う | 使わない |

推定で使う調整は、どれも本文を変えないか、変える箇所を減らす向きにのみ働く。推定が外れても、本文の書き換えは種類と読者を決めないときより増えない。

## 7. 読者の3段階

| 値 | 意味 | 用語の扱い | 文の長さと省略 |
|---|---|---|---|
| expert | 文書の分野の用語と前提を共有している | 用語、略語、識別子を残す。説明を追加せず、説明が必要な所も返さない | 分野で普通の省略を残す。長い文を分けるのは読み違いを特定できたときのみ |
| informed | 一般の技術や業務の言葉は分かるが、この分野のみの略語、社内の呼び名、前提の手順は知らない | 一般の技術語と業務語は残す。分野の外で通じにくい言葉と社内の呼び名は、指定されたときのみ原文と資料の説明で言い換えるか添え、他は返す | expert と同じ |
| general | 分野の用語と前提を知らない | 説明のない用語は、指定されたときのみ、原文と資料の説明か同じ範囲を指す普段の言葉で言い換えるか添え、他は返す | 9章 |

- 技術の文書でないとき、informed は「仕事の文書を読み慣れていて、一般の業務の言葉は分かる人」と読む。
- 開発者向け（読者が expert か informed で、本文がソフトウェアの話）では、識別子が主語の文（`scheduler` が失敗したジョブを再投入する）を擬人化として修正しない。「コードが語る」のような本当の擬人化は修正する。general でも識別子は言い換えない。

## 8. 用語の扱い

| 分類 | 例（合成） | expert | informed | general |
|---|---|---|---|---|
| A 原文か資料に説明がある用語 | 「TTL（キャッシュを残す時間）」と原文にある | 残す | 残す | 残す |
| B 説明のない分野の用語と略語 | 冪等、p95、減価償却、発注点 | 残す | 一般の技術語と業務語（API、サーバー、売上原価）は残す。分野のみの言葉は、資料に定義があり指定されたときのみ言い換えるか添え、他は返す | 資料に定義があり指定されたときのみ言い換えるか添え、他は返す |
| C 社内の呼び名、内部の略語、プロジェクト名 | 青環境、P1対応、月次締め会 | 残す | 返す（資料に説明があり指定されたときは添える） | 同左 |
| D 直訳の言葉、AIの造語、意味のぼやけた流行語 | 版、回帰、判断OS、解像度 | SKILL.md「専門用語と名称の扱い」と「内容に合わない大げさな名詞の整理」のとおり（slop-catalog.md 2章、5章） | 同左 | 同左 |
| E 識別子、コード、画面の項目名、製品名、法令の用語、数値と単位 | `retry_limit`、「保存」ボタン、PostgreSQL | 残す（識別子が主語の文も残す） | 同左 | 残す。言い換えない。必要なら返す |
| F 同じ範囲の普段の言葉がある外来語 | アサイン、アジェンダ | 残す | 残す | 指定されたときのみ、同じ範囲の普段の言葉に言い換えてよい |

言い換えてよいのは、次の全てを満たすときのみ。

1. 利用者が informed か general を指定した（確認した答えを含む）。推定では言い換えない。
2. 言い換えの言葉が原文か資料の定義から取れる。または、普段の言葉で指す範囲が同じと言える（狭めも広げもしない。分類 F）。モデルが知っている一般の知識で定義を書かない。それは原文にない説明になる。
3. 言い換えが1つに決まる。
4. 「変えたところ」に「用語 → 言い換え（読者: general）」と1行で書く。

言い換えない言葉は、分類 E の全て、原文で定義された言葉、見出しや表の項目名と本文で対応している言葉、引用の中の言葉。提供された定義や値と状態の対応を説明に使う規則（SKILL.md「情報を追加しない」）は、読者によらず同じに適用する。

## 9. 文の長さと省略

- 種類ごとの長さと省略は、doc-types の各ファイルの3章に従う。
- general を指定されたときのみ、1文に用件が2つ以上あり、接続語で関係を残せる文を分けてよい（SKILL.md「文長と読点の調整」の範囲）。推定の general では分ける範囲を広げない。
- 数値の目安は新しく作らない（平均30〜45字の目安は gemini-syntax.md 原則7）。

## 10. 「ここに説明が必要です」の書き方

- 書く欄は「書き手に確かめたい点」。形は `- ここに説明が必要です: 「TTL」（3段落目。原文と資料に説明がない）`。本文には入れない。
- 3点まで。確かめたい点の3点とは別に数える。多ければ、見出し、最初の段落、何度も出る言葉の順番に選び、「ほかに N か所」と添える。
- 言葉ごとに説明の文案を書かない。説明は書き手が書く（SKILL.md 3章の「書き手に確かめたい点」）。
- 読者が expert のとき、読者を決めないとき、本文のみの指定のときは出さない。
- 社外の読み手（関係を指定されたとき）の社内の呼び名には、「説明を足すか、出さないかは書き手が決める」と添えてよい。段階が expert なら、このときも出さない。
- 確かめたい点は、原文そのものの意味が決まらない所。説明が必要な所は、書き手には分かっているが読者には足りない所。同じ言葉を両方に書かない。新規作成でも、資料に説明がなければ追加せずに返す。

## 11. 読者像

- 「入社2年目の営業担当」「購買部の課長」のような読者像は、3段階のどれに当たるかを決める手がかりにする（読者像の分野と文書の分野が同じなら expert、違うが技術や業務の言葉に慣れていれば informed、それ以外は general）。どの言葉に説明が必要かも、決めた段階で決める。
- 書き手と読み手との関係の扱いは persona.md。敬語を変えるのは persona.md 7章の範囲（関係を言われたときに敬語を上げ、揃えること）のみ。構成、常体と敬体、主張、例は変えない。
- 読者像は lint に渡さない。
- 「初心者向けに」「やさしく」と頼まれたときは、言葉と説明の順序を易しくし（8章と9章の範囲）、読み手を大人として扱う。子ども向けの語尾（〜だよ、〜しようね、〜かな？）、ひらがなへの開きすぎ、「大丈夫！」「安心してね」のような励ましの決まり文句は追加しない。原文がその口調のときは、依頼がなければ変えない。

## 12. 示し方

- 確認の記録の最初の行に `- 書き手・読み手・場面: 書き手: 決めていない／読み手: expert（指定）／場面: incident（推定）` のように書く（相手と関係の書き方は persona.md 9章）。決めなければ「決めていない」。指定と本文の形が食い違えば、行の終わりに短く添える。
- lint に付けた `--doc-type` と `--reader` は、確認の記録の行と合わせる。
- 決めた種類と読者のみを付ける。候補を減らすために種類を付けない。
- 推定したことや説明が必要なことを、本文の中に書かない。本文のみの指定では、確認の記録ごと出さない。
- 利用者が種類か読者を修正したら、新しい依頼として書き直し、lint もその種類と読者でかけ直す。

## 13. 種類と外す規則の全体の表

SKILL.md 1章の規則のうち適用しない範囲は、種類ごとの `references/doc-types/` のファイルのとおり（SKILL.md 2章 Step 1）。lint が除外する規則と根拠は次のとおり。

| 種類 | lint で外す規則 | 根拠 |
|---|---|---|
| pr | excess_list | 変更点と確認したことは並列が明確な箇条書き |
| article | なし | |
| incident | excess_list | 時系列の箇条書き |
| proposal | なし | |
| minutes | bold_label_list、excess_list、sentence_end_repetition | 項目に分けた構造とラベルが普通。同じ文末の連続は議事録では人の文にも多い |
| manual | excess_list | 番号つきの手順は並列が明確な箇条書き |
| slides | bare_verb_chain、bold_label_list、cleft_list_ending、count_declaration、excess_list、short_summary_heading | 短い見出しと箇条書き、目次の数の宣言、まとめのページが普通の構成。箇条で強調として選ぶ「〜のは、A、B、C。」と、主語を書かずに動詞を並べる箇条も普通の書き方 |
| essay | bare_verb_chain、metaphor_label | 読み取れる比喩を残し、成り立たない比喩を修正するのは、エージェントが doc-types/essay.md に従って行う。見出しの短い比喩と、動詞を並べて止める形は書き手の文体として除外する。metaphor_verb の候補（エッセイの比喩動詞）は除外しない |
| formal | なし | 硬い言葉の言い換えと「〜を行う」の形は、エージェントが適用しない（doc-types/formal.md） |
| promo | bare_verb_chain、emoji_prohibited、fragment_run、metaphor_label | 書き手が気持ちや勢いを表す絵文字と、本文で評価の言葉を短く重ねる型（安い。うまい。早い。）、見出しの短い比喩、動詞を並べて止める形は普通の書き方。「！」、見出しのキャッチコピー、勢いのある言葉と強める言葉、同じ褒め言葉の繰り返しは、エージェントが doc-types/promo.md に従って残す |
| mail | emoji_prohibited、meta_filler（返信と結びの5つの型のみ） | 宛名、挨拶、結び、署名と、相手への返信の言葉（「ご質問ありがとうございます」「参考になれば幸いです」など）は普通の書き方。書き手が気持ちを表す絵文字も残す。meta_filler の他の型（誇張や中身のない前置き）は除外しない。敬語の度合い、クッション言葉、チャットの口語は、エージェントが doc-types/mail.md に従って残す |
| paper | なし | 慎重な言い方、引用の書き方、専門用語、「である」調、条件と結果をまとめた長い文は、エージェントが doc-types/paper.md に従って残す |
| script | bare_verb_chain、fragment_run、metaphor_label、sentence_end_repetition | 台詞では短い文を重ねる形、同じ語尾の続き、主語のない動詞の並びが普通に出る。見出しの短い比喩も題として残す。台詞の口調と表現は、エージェントが doc-types/script.md に従って残す |

- lint は除外した候補の件数のみを出す。中身は `--doc-type` を付けずに実行すると見られる。
- bold_not_rendered（表示されない太字）と metaphor_verb は、どの種類でも除外しない。fragment_run（「速い。軽い。安い。」の型）は promo と script のときのみ除外する。
- pause_comma（短い主語や主題、目的語のすぐ後の読点）は、3.3.0 から種類を指定しないときも出る。promo と script では出さない。
- dialogue_period（台詞の最後の句点）は script のときのみ、narrative_density（読み物の一人称と数字）は essay のときのみ、slide_comma（見出しの読点と、1行の箇条の間を作るのみの読点。見出しでは文書の題を除き、カギ括弧や引用符の中と数字の区切りの他の読点を全て候補に出す）は slides のときのみ出す。種類を指定しないときと他の種類では出さない。
